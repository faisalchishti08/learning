"@Transactional & declarative transaction management"

← Back to checklist

1. What it is

@Transactional is a Spring annotation that wraps a method in a database transaction automatically: Spring begins a transaction before the method runs, commits it if the method returns normally, and rolls it back if the method throws an (unchecked) exception. This is called declarative transaction management, because you declare the boundary with an annotation instead of writing begin/commit/rollback calls by hand.

2. Why & when

Managing transactions manually means wrapping every multi-step database operation in explicit try/catch/finally blocks that begin, commit, and roll back — repetitive, and easy to get subtly wrong (forgetting a rollback on one exception path). @Transactional moves that logic into a Spring-generated proxy around your method, the same mechanism @Cacheable uses, so you only need to mark the method boundary. Apply it to any service method that performs multiple related writes that must succeed or fail together — the exact scenario ACID's atomicity guarantee is meant for.

3. Core concept

The proxy wraps the whole method as one transaction:

@Service
public class TransferService {

    @Transactional
    public void transfer(Long fromId, Long toId, int amount) {
        Account from = accountRepository.findById(fromId).orElseThrow();
        Account to = accountRepository.findById(toId).orElseThrow();

        from.setBalance(from.getBalance() - amount);
        to.setBalance(to.getBalance() + amount);

        accountRepository.save(from);
        accountRepository.save(to); // if this line throws, the debit above is ALSO rolled back
    }
}

Both save calls happen inside one transaction; if the second one throws, Spring rolls back the entire transaction, including the first save, leaving the database exactly as it was before transfer was called.

Rollback rules — by default, unchecked exceptions only: Spring only triggers an automatic rollback for unchecked exceptions (subclasses of RuntimeException) by default; a checked exception does not trigger a rollback unless you explicitly configure it with @Transactional(rollbackFor = SomeCheckedException.class). This surprises many developers who assume any thrown exception rolls back the transaction.

The same proxy limitation as @Cacheable: because @Transactional also works via a Spring-generated proxy, calling a @Transactional method from another method in the *same* class (this.transfer(...)) bypasses the proxy and runs with no transaction at all — the same self-invocation gotcha that affects @Cacheable.

Propagation — nested @Transactional calls: if a @Transactional method calls another @Transactional method (through the proxy, on a different bean), the default propagation setting joins the inner call into the same, already-active transaction, rather than starting a fully independent one.

5. Runnable example

Artifact: a minimal Java sketch modeling the @Transactional proxy's commit/rollback behavior

import java.util.*;

public class TransactionalSim {

    static final Map<Long, Integer> accounts = new HashMap<>();

    // Simulates the transactional log Spring/JDBC maintains during an in-progress transaction.
    static Map<Long, Integer> pendingChanges;

    // Simulates the proxy Spring generates for @Transactional - begins, then commits or rolls back.
    static void runTransactional(Runnable methodBody) {
        pendingChanges = new HashMap<>(accounts); // BEGIN TRANSACTION: work happens on a pending copy
        try {
            methodBody.run(); // the real @Transactional method body runs here
            accounts.putAll(pendingChanges); // COMMIT: apply every pending change at once
            System.out.println("  COMMIT: transaction applied");
        } catch (RuntimeException e) {
            System.out.println("  ROLLBACK: " + e.getMessage() + " (no pending changes were applied)");
            // pendingChanges is simply discarded: accounts is untouched
        } finally {
            pendingChanges = null;
        }
    }

    // Mirrors a @Transactional service method: two related writes, treated as one unit.
    static void transfer(long fromId, long toId, int amount, boolean simulateFailureAfterDebit) {
        int fromBalance = pendingChanges.get(fromId);
        pendingChanges.put(fromId, fromBalance - amount); // "debit" - only in the pending copy so far

        if (simulateFailureAfterDebit) {
            throw new RuntimeException("credit step failed after debit was already applied");
        }

        int toBalance = pendingChanges.get(toId);
        pendingChanges.put(toId, toBalance + amount); // "credit"
    }

    public static void main(String[] args) {
        accounts.put(1L, 100);
        accounts.put(2L, 50);

        System.out.println("attempting a successful transfer:");
        runTransactional(() -> transfer(1L, 2L, 30, false));
        System.out.println("balances: " + accounts);

        System.out.println("attempting a transfer that fails AFTER the debit step:");
        runTransactional(() -> transfer(1L, 2L, 20, true));
        System.out.println("balances (unchanged - the partial debit was rolled back too): " + accounts);
    }
}

How to run: save as TransactionalSim.java, run java TransactionalSim.java (JDK 17+). A real Spring Boot app needs @Transactional on the service method and a configured PlatformTransactionManager (auto-configured by spring-boot-starter-data-jpa).

6. Walkthrough

  1. runTransactional starts by copying accounts into pendingChanges — modeling BEGIN TRANSACTION, where changes are not yet visible outside the transaction.
  2. The first call runs transfer(1L, 2L, 30, false), which debits pendingChanges for account 1 and credits it for account 2, then returns normally without throwing.
  3. Because methodBody.run() completed without an exception, runTransactional copies every entry from pendingChanges back into accounts — modeling COMMIT — and the printed balances show {1=70, 2=80}.
  4. The second call runs transfer(1L, 2L, 20, true), which debits account 1 in pendingChanges (fromBalance - amount) and then immediately throws a RuntimeException, *before* the credit step ever runs.
  5. runTransactional's catch block catches that exception and never calls accounts.putAll(pendingChanges) — the partial debit that happened inside pendingChanges is simply discarded, and the printed balances afterward confirm accounts is completely unchanged, exactly matching what @Transactional's automatic rollback on an unchecked exception guarantees.

7. Gotchas & takeaways

Gotcha: by default, @Transactional only rolls back on unchecked exceptions; a method that throws a checked exception (like IOException) will still commit whatever partial work already happened, unless you explicitly add rollbackFor = Exception.class (or the specific checked exception type) — a frequent source of "why didn't my transaction roll back" bugs.
  • @Transactional moves manual begin/commit/rollback boilerplate into a Spring-generated proxy, wrapping the annotated method as one atomic unit.
  • The proxy-based mechanism means self-invocation (calling a @Transactional method from within the same class) silently skips the transaction entirely — call through another Spring bean instead.
  • Related concepts: ACID properties (atomicity and consistency are exactly what @Transactional provides at the application layer), Spring Data JPA & repositories (repository save calls are commonly wrapped together inside a @Transactional service method).
