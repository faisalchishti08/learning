## 1. What it is

The **Spring Cache abstraction** lets you add caching to a method with annotations, without writing any cache-lookup code yourself. **`@Cacheable`** wraps a method so its result is cached by its arguments — the method body only runs on a cache miss. **`@CacheEvict`** removes an entry from the cache, typically applied to the method that updates the underlying data.

## 2. Why & when

Writing cache-aside logic by hand (check cache, on miss call the real method, then store the result) means repeating that same boilerplate in every method you want to cache. Spring's abstraction moves that boilerplate into a proxy generated around your method, so caching becomes a one-line annotation. Use it for read-heavy service methods backed by a database, where the arguments naturally form a good cache key (a single ID, a simple query).

## 3. Core concept

**How `@Cacheable` works:** Spring wraps the annotated method in a proxy. When the method is called, the proxy first checks the named cache using a key derived from the method's arguments (by default, the arguments themselves). On a hit, the proxy returns the cached value directly, and the real method body never runs. On a miss, the proxy calls the real method, stores its return value under that key, and returns it — exactly the cache-aside pattern, generated for you.

```java
@Service
public class UserService {

    @Cacheable("users")
    public User findById(Long id) {
        System.out.println("querying database for " + id); // only runs on a cache miss
        return database.findById(id);
    }

    @CacheEvict(value = "users", key = "#id")
    public void updateUser(Long id, User updated) {
        database.save(updated); // write to the database
        // the proxy removes cache "users" entry for #id after this method returns
    }
}
```

**Why the proxy only intercepts external calls:** Spring's annotation-driven caching works by wrapping the bean in a proxy at startup; a call from *outside* the bean (through the proxy) is intercepted, but a method calling `this.findById(...)` *internally*, from another method in the same class, bypasses the proxy entirely and skips caching — a common gotcha covered below.

**`@CacheEvict` on write:** applying `@CacheEvict` to the update method removes the stale entry so the next `@Cacheable` call is forced to miss and reload — this is explicit invalidation, wired declaratively instead of by hand.

## 5. Runnable example

### Artifact: a minimal Java sketch modeling Spring's `@Cacheable` / `@CacheEvict` proxy behavior

```java
import java.util.HashMap;
import java.util.Map;
import java.util.function.Function;

public class SpringCacheSim {

    // Simulates the proxy Spring generates around a @Cacheable / @CacheEvict method.
    static class CacheableProxy<K, V> {
        private final Map<String, Map<K, V>> caches = new HashMap<>();
        private final Function<K, V> realMethod;
        private final String cacheName;
        int realMethodCalls = 0;

        CacheableProxy(String cacheName, Function<K, V> realMethod) {
            this.cacheName = cacheName;
            this.realMethod = realMethod;
        }

        V cacheable(K key) {
            Map<K, V> cache = caches.computeIfAbsent(cacheName, n -> new HashMap<>());
            if (cache.containsKey(key)) {
                return cache.get(key); // @Cacheable hit: real method body skipped
            }
            realMethodCalls++;
            V value = realMethod.apply(key); // @Cacheable miss: run the real method
            cache.put(key, value);
            return value;
        }

        void cacheEvict(K key) {
            Map<K, V> cache = caches.get(cacheName);
            if (cache != null) cache.remove(key); // @CacheEvict(key = "#id")
        }
    }

    public static void main(String[] args) {
        Map<Long, String> database = new HashMap<>();
        database.put(42L, "Alice");

        CacheableProxy<Long, String> userService = new CacheableProxy<>("users", id -> {
            System.out.println("  querying database for " + id);
            return database.get(id);
        });

        System.out.println("findById(42): " + userService.cacheable(42L)); // miss, queries DB
        System.out.println("findById(42): " + userService.cacheable(42L)); // hit, no query
        System.out.println("real method calls so far: " + userService.realMethodCalls);

        // updateUser: write to DB, then evict, mirroring @CacheEvict(key = "#id")
        database.put(42L, "Alice Smith");
        userService.cacheEvict(42L);

        System.out.println("findById(42) after update: " + userService.cacheable(42L)); // miss again, fresh
        System.out.println("real method calls total: " + userService.realMethodCalls);
    }
}
```

**How to run:** save as `SpringCacheSim.java`, run `java SpringCacheSim.java` (JDK 17+). A real Spring app needs `@EnableCaching` on a configuration class and a `CacheManager` bean (backed by an in-memory `ConcurrentMapCacheManager` for simple cases, or Redis for a distributed cache).

## 6. Walkthrough

1. `userService.cacheable(42L)` finds no entry in the `"users"` cache, so it calls the real method (printing `"querying database for 42"`), stores `"Alice"`, and returns it — `realMethodCalls` becomes `1`, mirroring a real `@Cacheable` miss.
2. The second `cacheable(42L)` call finds `42L` already cached and returns `"Alice"` directly, without printing the query line or incrementing `realMethodCalls` — mirroring a `@Cacheable` hit, where the annotated method body never runs.
3. `database.put(42L, "Alice Smith")` simulates the update method writing new data.
4. `userService.cacheEvict(42L)` removes the `"users"` cache entry for key `42L`, mirroring `@CacheEvict(value = "users", key = "#id")` running after the update method's body.
5. The final `cacheable(42L)` call misses again (the entry was evicted), calls the real method a second time, and returns the fresh `"Alice Smith"` — `realMethodCalls` ends at `2`.

## 7. Gotchas & takeaways

> **Gotcha:** calling a `@Cacheable` method from another method in the *same* class (`this.findById(id)`) bypasses the Spring-generated proxy entirely, so caching silently does not happen — this is a direct consequence of how Spring's proxy-based AOP works, and it catches most people at least once.

- `@Cacheable` and `@CacheEvict` turn the cache-aside pattern into a one-line annotation, generated as a proxy around your bean.
- The default cache key is derived from the method's arguments; for methods with multiple or complex parameters, specify the key explicitly with SpEL (e.g. `key = "#id"`).
- Related concepts: [Cache-aside (lazy loading)](0045-cache-aside-lazy-loading.md) (the pattern this abstraction automates), [Redis / Memcached as a cache provider](0060-redis-memcached-as-a-cache-provider.md) (a common backing store, wired in via a `CacheManager`).
